# DECISIONS.md — سجل القرارات المعمارية (ADR) — حجوزاتي

> كل قرار مهم يُسجَّل هنا مع السبب، ليبقى مرجعًا ثابتًا لأي مطور أو AI Agent لاحقًا.

## ADR-001: Flutter كإطار عمل
**القرار**: بناء التطبيق باستخدام Flutter لدعم Android وiOS من قاعدة كود واحدة.
**السبب**: طلب صريح من صاحب المشروع؛ كما توفر Flutter أداءً قريبًا من Native وسرعة تطوير عالية لتطبيق متعدد الشاشات مثل حجوزاتي.

## ADR-002: Riverpod لإدارة الحالة
**القرار**: استخدام `flutter_riverpod`.
**السبب**: Type-safe، يدعم الحالات غير المتزامنة (Loading/Data/Error) بشكل مدمج، ويعمل كطبقة حقن اعتمادات (DI) في الوقت نفسه دون الحاجة لمكتبة DI منفصلة — مناسب لتدفق حجز معقد يحتاج حالة مركزية (Booking Draft) ثابتة عبر عدة شاشات.

## ADR-003: go_router للتنقل
**القرار**: استخدام `go_router` كحل Navigation مركزي.
**السبب**: Routing تصريحي مناسب لعدد الشاشات الكبير، دعم مدمج لـ Deep Links مستقبلًا (متطلب صريح)، وتكامل سلس مع Riverpod للتوجيه الشرطي (Route Guards).

## ADR-004: Feature-based Clean Architecture مبسّطة
**القرار**: تقسيم الكود حسب Feature، وداخل كل Feature ثلاث طبقات (Presentation/Domain/Data).
**السبب**: فصل واضح بين منطق العمل والواجهة والبيانات (طلب صريح)، مع سهولة إضافة/تعديل Feature بمعزل عن الباقي، وقابلية استبدال مصدر البيانات (Mock → API حقيقي) دون كسر الطبقات الأخرى.

## ADR-005: بدون مكتبة Dependency Injection منفصلة
**القرار**: الاعتماد على Riverpod Providers للـ DI بدل مكتبات مثل `get_it` أو `injectable`.
**السبب**: تبسيط المشروع وتقليل طبقات التعقيد؛ Riverpod يوفر نفس الفائدة (استبدال Repository في الاختبارات عبر Overrides) دون أدوات إضافية.

## ADR-006: التوطين عبر ARB Files
**القرار**: استخدام `flutter_localizations` + ملفات ARB لكل لغة (ar/en، مع بنية جاهزة لـ fa).
**السبب**: الحل الرسمي المدعوم من Flutter، يضمن عدم وجود نصوص Hard-coded ويُسهّل إضافة لغات جديدة (كالفارسية) لاحقًا بدون تغيير هيكلي.

## ADR-007: استراتيجية Backend مؤجَّلة (Mock أولًا)
**القرار**: بناء كل Repository في المراحل المبكرة (Phase 04–18) ضد Data Source وهمي (Mock) يحاكي شكل استجابة API حقيقية، ثم استبداله بالكامل في Phase 19.
**السبب**: يسمح ببناء واختبار كل الميزات والتفاعلات الحقيقية (وفق NO FAKE INTERACTIONS POLICY) دون انتظار جاهزية Backend فعلي، مع ضمان أن الانتقال لاحقًا يمس طبقة Data فقط دون Domain أو Presentation.

## ADR-008: استراتيجية التخزين المحلي
**القرار**: تخزين خفيف (تفضيلات، لغة، مسودة حجز غير مكتملة) عبر حل تخزين محلي بسيط (مثل `shared_preferences`/`hive`، يُحسم الاختيار النهائي عند Phase 01).
**السبب**: لا حاجة لقاعدة بيانات محلية معقدة في هذه المرحلة؛ البيانات الرئيسية مصدرها الفندق/الحجز عبر Repository وليست محلية بطبيعتها.

## ADR-009: استراتيجية الخرائط
**القرار**: تأجيل اختيار مزوّد الخرائط النهائي إلى Phase 17، مع تجهيز الواجهة (`latitude/longitude` في نماذج Hotel وDestination) من الآن.
**السبب**: تجنّب قفل قرار تقني (Google Maps مقابل بديل آخر) قبل الحاجة الفعلية له، مع ضمان أن النماذج جاهزة لأي مزوّد يُختار لاحقًا.

## ADR-010: استراتيجية QR Code
**القرار**: توليد QR Code محليًا على الجهاز من بيانات الحجز المؤكد (`bookingId` + بيانات أساسية) عبر مكتبة توليد QR قياسية، دون الحاجة لخدمة خارجية.
**السبب**: أبسط وأسرع للـ MVP، ولا يتطلب اتصال Backend لإظهار القسيمة فور التأكيد.

## ADR-011: استراتيجية الاختبار
**القرار**: تغطية إلزامية بثلاث مستويات (Unit للـ Domain، Repository/Data tests، Widget tests للـ Presentation) لكل Feature قبل اعتباره مكتملًا.
**السبب**: يضمن الالتزام بـ Definition of Done وNO FAKE INTERACTIONS POLICY، ويمنع اعتبار أي شاشة "جاهزة" دون التحقق من عملها الفعلي.
